# 운영 DB 복원·R2 대조 실행 기록 — 2026-10-09

**운영 DB 백업·로컬 복원·migration에 이어 기존 원본 59개와 사용처 66행의 로컬 등록, 데이터 보존·권한·재실행 검증을 완료했다. 운영 배포와 기존 콘텐츠의 브라우저 전체 E2E는 아직 완료하지 않았다.** 2026-10-10 추가 검증과 기존 서버 업데이트 결정은 9–10절에 기록한다. 실행 순서는 [운영 DB·R2 전환 계획](./production-db-r2-migration-plan.md)을 따른다.

운영 DB에는 조회·덤프만 실행했다. R2는 목록·HEAD에 이어 9절에서 조건부 GET으로 원본을 검증했다. 검증용 임시 본문은 처리 후 제거했다. 운영 DB/R2 쓰기, R2 파일 복사·삭제, 앱 중단, DNS·버킷 설정 변경은 실행하지 않았다. 전체 목록과 증거는 Git/Docker context 밖의 접근 제한 폴더에 저장한다. 이 문서에는 DB 비밀번호, 자격 증명, 객체별 경로와 사용자 식별자를 포함하지 않는다.

## 1. 확인한 운영 환경

- OS: Ubuntu 24.04.4 LTS. Docker Compose로 앱과 DB를 실행 중이다.
- DB: PostgreSQL **16.15**, `online_glia`. `db:5432`는 Compose 내부 주소다.
- DB 시각: UTC. locale/ctype: `en_US.utf8`. 확장: `plpgsql 1.0`, `pgcrypto 1.3`.
- DB 크기: 조회 당시 15,006,743 bytes. public 테이블 69개, 완료 migration 16개, 미검증 제약 0개.
- 백업 복원본: 3,259행. 이 중 migration 이력 16행을 제외한 기존 업무 데이터는 68개 테이블, 3,243행이다.
- 주요 행 수: 사용자 15, 코스 2, 레슨 12, 콘텐츠 12, 코칭 회차 121, 주문 17, 수강 9.
- 서버 checkout revision: `2882473783f651e4e8caf2ed44c3eb1f1d3b0209`. 실행 이미지 식별자는 별도 보관했다. checkout revision만으로 실행 이미지의 소스가 동일하다고 단정하지 않는다.
- 운영에는 새 미디어 테이블 다섯 개가 아직 없다.

현재 접속한 서버는 기존 운영 서버로 확인했다. 이번 배포가 같은 서버의 업데이트인지, 별도 서버 이전인지와 새 서버의 접속 정보는 확정할 항목이다.

## 2. 백업과 로컬 복원

2026-10-09 14:24:26–14:24:27 KST에 전체 custom-format `pg_dump`를 스트리밍으로 받았다. 운영 쓰기를 중단하지 않았으므로 **리허설용 백업이며 최종 전환용 백업이 아니다.**

- 원본 아카이브: 416,857 bytes. 평문 덤프 파일을 저장하지 않고 암호화해 보관했다.
- 암호화 키, 덤프, 해시·시각·버전 manifest는 제한 폴더에 보관한다. 디렉터리는 0700, 파일은 0600이다. 키는 Git과 배포 이미지에 포함하지 않는다.
- 실제 복호화 스트림의 SHA-256을 원본 스트림의 해시와 비교한 뒤 빈 DB에 `pg_restore --exit-on-error`로 전체 복원했다.
- 로컬은 운영과 같은 PostgreSQL 16.15 공식 컨테이너를 사용한다. 접근은 `127.0.0.1:54701`로 제한했다.
- `source_snapshot`: 복원 원본 보존용 DB. 새 migration이나 테스트 행을 적용하지 않았다.
- `migration_rehearsal`: 원본 DB를 복제한 검증용 DB. 전용 Prisma config로 이 DB에만 migration을 적용했다.

로컬 복원에는 `--no-owner --no-acl`을 사용해 격리 계정이 소유하도록 했다. 따라서 운영 역할·권한 재현까지 통과했다는 의미는 아니다. 최종 대상 서버에는 소유 역할·권한·예약 작업·환경변수를 별도로 준비해야 한다. 로컬 복원 DB로 앱이나 외부 발송·결제·예약 작업은 실행하지 않았다.

## 3. DB 검증 결과

기존 16개 migration 파일의 SHA-256이 운영 이력과 모두 일치했다. `20261007090000_media_asset_foundation`만 적용되어 로컬 검증 DB는 17개 migration 상태다.

- **기존 68개 테이블, 3,243행의 행 수와 테이블별 데이터 지문이 모두 동일하다.** migration 이력만 의도대로 1행 증가했다.
- MediaAsset·MediaFile·MediaUsage·MediaUpload·MediaDeletionJob에 대응하는 다섯 테이블이 생성됐고 모두 비어 있다. 기존 자산 등록/backfill은 아직 실행하지 않았다.
- SQL의 명시적 인덱스 17개가 유효하고 함수 11개, 트리거 10개가 존재한다. 일관성 트리거 5개는 활성 상태의 `DEFERRABLE INITIALLY DEFERRED`다.
- 미디어 테이블의 CHECK 37개, FK 10개, PK 5개, UNIQUE 제약 5개 및 제약 트리거 5개를 확인했다. public 전체에 미검증 제약은 없다. 부분 UNIQUE 인덱스는 위 명시적 인덱스 수에 포함된다.
- `media_assert_asset(target text)`가 설치돼 있어 CUID 문자열 ID를 받는다.
- 실제 SQL로 원본 없는 자산의 지연 제약 거절, 유효한 PENDING 원본 쌍 허용, object key 변경 거절, 중복 원본 거절, 원본의 현재 파일 지정 거절, 내용 검증 없는 READY 거절을 확인했다. 여섯 검사는 모두 롤백했고 테스트 행이 남지 않았다.

추가로 경로 별칭 대조의 회귀 검사 두 개를 포함한 `npm run test:media-db` **230개가 모두 통과**했다. 이 통합 검사 실행 환경은 PostgreSQL 14.16과 가짜 저장소다. 위의 운영 복원·migration·여섯 제약 검사는 별도로 PostgreSQL 16.15에서 실행했다. 두 결과를 실제 R2 업로드/재생 시험 완료로 해석하지 않는다.

## 4. R2 대조 결과와 경로 차이

전체 목록은 **152개 객체, 8,190,664,580 bytes**다. 물리 경로 분류는 아바타 2개, 코칭 71개, 커뮤니티 34개, 코스 45개다. 이 최초 목록 대조 단계에서는 파일 본문을 읽지 않았다. 후속 본문 검증은 9절에 구분한다.

### 4.1 기존 endpoint가 만든 추가 prefix

운영 `R2_ENDPOINT`에는 계정 호스트 뒤에 `/버킷명`이 붙어 있고 SDK는 `forcePathStyle`을 사용한다. 기존 앱이 논리 key로 요청하는 위치와 정상 계정 endpoint에서 조회하는 실제 key가 다음처럼 다르다.

```text
본문·기존 앱의 논리 key: coaching/{회차}/images/{파일}
R2 목록의 실제 key:    {버킷명}/coaching/{회차}/images/{파일}
```

이 차이를 무시한 첫 대조에서는 103개 사용 관계가 목록 누락으로 표시됐다. 실제 운영 요청 방식과 정규화한 endpoint + 실제 key의 HEAD를 쌍으로 확인했다.

- DB에서 확인한 고유 논리 경로 96개 중 **94개는 양쪽 모두 200이고 크기·ETag가 일치**했다. 캡처한 R2 목록의 메타데이터와도 일치했다.
- 나머지 **2개는 커뮤니티 게시물의 이미지 1개·영상 1개**이며, 양쪽 HEAD 모두 404이고 전체 목록에도 없다. 누락 위치와 게시물 식별 정보는 제한 폴더의 별도 보고서에 보관했다. 자동으로 본문을 고치거나 파일을 대체하지 않았다.
- 코스·코칭 본문 133개에서 추출한 고유 경로 59개는 매핑 후 목록 누락이 0개다. 이는 존재 확인이며 권한·브라우저 재생·탐색 검증은 아니다.

**배포에서 endpoint만 계정 호스트로 바꾸면 기존 주소가 깨질 수 있다.** 반대로 실제 key를 DB에 등록하면서 이전 endpoint를 그대로 쓰면 prefix가 다시 붙을 수 있다. 새 미디어 등록과 endpoint 정규화는 legacy 논리 key → 실제 object key의 읽기 호환을 함께 검증한 뒤 적용해야 한다. 아바타·커뮤니티·수업자료 등 새 미디어 테이블 밖의 소비자도 포함한다. 기존 파일을 새 경로로 복사할 필요는 없다.

이번 매핑은 조사용 config다. 앱 라우팅이나 운영 설정은 변경하지 않았다. 서버만 먼저 이전한다면 검증된 기존 앱과 기존 endpoint를 함께 유지하는 것이 우선이다.

### 4.2 사용처와 보관 여부

32개 테이블의 627개 본문·필드 출처를 대조했다. 확인된 명시적 별칭을 반영한 결과:

- 현재 출처에서 참조된 객체: **94개**.
- 코스·코칭 대상 경로지만 참조를 관측하지 못한 객체: **50개**.
- 참조를 관측하지 못했고 이번 코스·코칭 자산 경로 범위 밖인 객체: **8개**.
- key에 담긴 회차/레슨 문맥이 현재 DB에 없는 객체: **9개**. 위 객체들과 중복되는 검토 항목이다.

50개와 8개는 삭제 대상이라는 뜻이 아니다. 보관 의사, 이전 콘텐츠, 범위 밖 소비자와 소유 근거를 확인할 때까지 유지한다. 새 미디어 테이블이 없으므로 등록 파일과 사용처 행은 모두 0개다. `UNREGISTERED_REFERENCE`는 아직 backfill하지 않은 상태를 보여 주며 새 장애가 발생했다는 뜻은 아니다.

미조사 후보로 감지된 `lesson_materials.contentType`은 6행 모두 MIME 값이고, `signup_drafts.avatarPresetId`는 값이 있는 행이 0개였다. 이 데이터 시점의 검토 결과를 상세 보고서에 남겼으며 도구의 경고를 임의로 삭제하지 않았다. DB 밖의 참조와 제외 테이블까지 조사 완료됐다는 의미는 아니다.

### 4.3 설정 확인의 한계

- CORS와 lifecycle 조회는 각각 403이다. **설정 없음이 아니라 현재 자격으로 확인하지 못한 상태**다.
- `R2_PUBLIC_BASE_URL`은 비어 있다. 이 값만으로 r2.dev나 공개 도메인이 꺼져 있다고 판단할 수 없다.
- 개인 자산 공개 전에는 관리 권한으로 버킷 공개 경로·CORS·수명 규칙을 확인해야 한다.
- ETag·HEAD·목록은 내용 SHA-256, 정상 디코딩, 재생, 권한 검사의 대체 수단이 아니다.

## 5. 이번에 보완한 도구

[대조 로직](../scripts/media-audit/reconcile.ts)이 DB에 등록된 URL key와 검증된 `keyAliases`를 사용해 물리 key가 다른 파일의 조사 범위·편집자 후보를 판단하도록 보완했다. 사용처 없는 기존 파일이 추가 prefix 때문에 모두 `OUT_OF_SCOPE`가 되던 문제를 고쳤다. 실제 object key는 그대로 출력하고, 확인되지 않은 prefix를 자동 제거하지 않는다. 소유 확정과 삭제 승인은 계속 하지 않는다.

[회귀 검사](../scripts/media-audit.integration.ts)는 별칭 없는 경우 추정 금지, 명시적 매핑, 한 객체의 여러 논리 문맥, 다른 버킷 격리, 등록된 URL key의 문맥 보존을 검증한다. `.dockerignore`에는 대조·리허설·백업 디렉터리와 덤프·비공개 보고서 파일의 제외도 추가했다.

## 6. 다음 단계와 배포 기준

1. **배포 대상 확정:** 현재 서버 업데이트인지 별도 서버 이전인지, 이번 공개 범위가 서버만인지 새 보관함까지인지 정한다.
2. **R2 읽기 호환:** 확인된 매핑으로 코스·코칭 외 소비자까지 읽기 경로를 설계한다. endpoint와 backfill을 함께 전환할 때의 계약을 테스트한다. 커뮤니티 누락 2개는 복구할 원본 또는 콘텐츠 처리 정책을 별도로 확인한다.
3. **테스트 저장소:** 비공개 테스트 버킷, 원본 읽기/테스트 쓰기 자격을 분리한다. 선택 객체 복사 manifest와 테스트 import를 준비하고 실제 이미지·영상·오디오의 업로드·권한·Range·재시도를 검사한다.
4. **보관함 공개 준비:** 운영 업로드 차단, 공개 경로, 기존 자산 backfill, 검증 자원 제한을 해결한다. 자동 삭제는 계속 비활성으로 둔다.
5. **운영 반영:** 테스트용 DB를 되돌려 넣지 않는다. 쓰기 중단 후 최종 원본 백업에 검증된 migration·변환만 적용한 반영용 DB와 확정 이미지를 배포한다. 새 쓰기가 시작된 뒤 이전 DB로 단순 교체하지 않는다.

현 단계 완료 범위는 **원본 확보·로컬 DB 복원·migration 보존 검증·R2 메타데이터 대조**다. 앱 기능/권한/미디어 재생의 실데이터 검증, 운영용 R2 설정·backfill, 대상 서버 반영과 전환은 남아 있다.

## 7. 후속 구현: R2 주소 호환

이어서 기존 논리 URL과 실제 R2 경로를 연결하는 코드를 구현했다. 기존 목록/HEAD에서 확인한 prefix 계약을 코드에 명시했으며 원본 객체나 본문을 바꾸지 않았다.

### 설정과 요청 계약

```dotenv
# 검증한 기존 운영 버킷에 새 앱을 배포할 때 함께 적용할 값. 아직 적용하지 않았다.
R2_BUCKET=online-glia
R2_ENDPOINT=https://ACCOUNT_ID.r2.cloudflarestorage.com
R2_LEGACY_KEY_PREFIX=online-glia/
```

계정 ID와 자격 증명은 기존 보안 설정에서 공급한다. endpoint의 `/online-glia` 경로는 제거하고, 확인된 prefix는 별도 설정으로 전달한다. 이 예시를 이전 운영 이미지에 먼저 적용하면 기존 URL이 깨질 수 있다. 새 코드는 경로가 붙은 endpoint를 거절하므로 **앱과 설정을 함께 전환**해야 한다. 되돌릴 때도 이미지와 endpoint/prefix 설정을 함께 복원한다.

- 기존 아바타·커뮤니티·Q&A·코스·코칭의 업로드/서명/읽기/기존 삭제는 논리 key를 받고 같은 실제 prefix를 사용한다. 수업자료 DB의 기존 `objectKey`도 이 legacy 계약에 해당한다.
- 등록된 `MediaFile.objectKey`는 실제 key이므로 다시 prefix를 붙이지 않는다. 새 보관함 원본과 staging도 `media/...` 위치를 그대로 사용한다.
- 공개로 취급되던 legacy URL이라도 매핑된 실제 객체가 개인 자산으로 등록돼 있으면 등록 자산의 권한을 먼저 검사한다. 서로 다른 등록 자산 두 개가 매칭되면 거절한다.
- 파일이 없다고 다른 key를 자동 탐색하지 않는다. 기존 커뮤니티 404 두 개도 숨기거나 다른 객체로 연결하지 않는다.
- 테스트 버킷은 조사로 확인된 prefix가 없으면 `R2_LEGACY_KEY_PREFIX`를 비운다. 신규 업로드의 운영 버킷 차단과 정리 worker의 운영 차단은 유지했다.

- 비활성 응답일 때 기존 코스·코칭 업로드를 사용한다. 설정 조회 실패나 신규 업로드 실패는 기존 API로 재전송하지 않는다. 기존 업로드 API 6개도 세션으로 인증하고, 코치의 레슨과 코스 ID 일치를 검사한다.
- PostgreSQL 14.16 격리 검사 **265개**, Chrome 편집기 검사 **13개**, TypeScript·변경 코드 ESLint·diff 검사를 통과했다. 테이블 수와 migration SQL은 변경하지 않았다.
- 깨끗한 이미지 설치에서 잠금 파일의 미완성 WASM 전이 의존성 항목을 발견했다. 배포용 Node 22/npm 10 환경에서 잠금 정보를 복구했고 기존 주요 패키지 버전은 유지했다.
- migration 이미지는 Next 빌드 의존성을 제거하고 Prisma 엔진을 빌드 때 포함한다. 처음 만든 이미지의 엔진 누락을 실제로 확인해 보완했으며, 수정 이미지에서 네트워크 없이 엔진 실행이 성공했다. 이미지 ID: `sha256:285320790fe073c760ceb5eb081c9d5986309a21469de9d04038b0f413d2405c`.
- 운영 Compose를 읽기 전용으로 해석해 기존 볼륨 `onlineglia_pgdata`와 앱 1.5GiB/DB 1GiB 한도를 확인했다. 앱 포트는 루프백, DB 5432는 호스트 게시 설정이다. 외부 방화벽 통과 여부를 시험하지 않았고 설정은 변경하지 않았다.

검증 기록은 저장소에서 제외된 `.media-audit/deployment-rollout-20261010/`에 보관한다. 운영 의존성 감사에서는 공개 보안 권고와 일치하는 버전이 확인되어 [운영 준비 3절](./production-existing-server-update-runbook.md#3-앱-교체-전에-해결할-배포-관문)에 보완 관문을 추가했다. 운영 서버·DB·R2의 변경이나 배포 완료를 의미하지 않는다.

### 11.1 보안 보완 전 후보 이미지의 실제 실행 검증

앱 후보 `sha256:ea504006ee7e89343896b2d00523a4b547cec64307b92830c1a5d0c25cab1b0e`는 Linux amd64, Node 22, 비루트 사용자 이미지다. 최적화 컴파일·TypeScript·정적 페이지 64개 생성까지 통과했다. 위 migration 이미지와 함께 `scripts/media-image-smoke.mjs`로 다음을 확인했다.

- 외부 통신이 차단된 임시 Docker 네트워크와 합성 PostgreSQL 16.15에서 migration 17개 적용, 미디어 테이블 5개 생성, migration 재실행 성공.
- `off/admin/all` 각각에서 실제 앱 HTTP 요청과 세션 쿠키로 인증·역할·보관함 공개 범위·예약/완료 중지를 확인했다. 위조 사용자 헤더만으로는 인증되지 않는다.
- 비루트 UID 1001, 이미지 내 `.env` 미포함, ffprobe/ffmpeg 실행과 합성 PNG·MP4·MP3 전체 디코딩을 확인했다. 컨테이너 1.5GiB 한도에서 OOM 종료는 없었다.
- 처음에는 internal 네트워크의 호스트 포트 게시가 지원되지 않아 중단됐다. 요청을 컨테이너 내부 HTTP로 변경한 두 번째 실행은 **5개 검사 그룹 모두 통과**했다. 실행별 임시 앱·DB·DB 볼륨·네트워크는 정리했다.

성공 기록은 `image-smoke-02.json`이다. 운영 R2·운영 DB 자격 증명은 제공하지 않았다. 짧은 합성 파일 검사이므로 운영 브라우저 재생·R2 업로드·대용량 처리 성능을 인증하지 않는다. 이 이미지는 보안 보완 전 비교 기준이며, 이후 의존성을 수정한 소스의 최종 배포 이미지로 사용할 수 없다.

## 12. 배포 의존성 보완 — 2026-10-10~11

공식 보안 권고와 npm 레지스트리의 호환 범위를 확인해 다음 잠금 버전을 반영했다.

- Next.js·eslint-config-next: **16.2.11 → 16.3.8**. 현재 React 19.2.4와 호환되는 패치가 포함된 16.3 계열을 사용한다. Cache Components 등 새 기능 설정은 추가하지 않았다.
- Tiptap 패키지 묶음: **3.29.2 → 3.31.4**, ProseMirror view: **1.42.2 → 1.42.6**. BlockNote 0.53.0이 허용하는 범위 안에서 정확한 peer 버전을 함께 맞췄다.
- sharp: **0.34.5 → 0.35.5**, fast-uri·source-map-js·nanoid와 관련 전이 의존성의 호환 패치를 적용했다. Next 내부에 남아 있던 오래된 PostCSS도 제거됐다.
- React·React DOM, BlockNote 3개 패키지, Prisma Client·CLI·PG adapter 버전, migration SQL과 업무 코드는 이번 의존성 보완에서 유지했다. `audit fix --force`나 Prisma 주요 버전 변경은 하지 않았다.

`npm audit --omit=dev --package-lock-only` 결과는 **critical 1/high 13/moderate 11 → critical 0/high 6/moderate 1**이다. 남은 7개 패키지 항목은 Prisma CLI·config·dev와 deepmerge-ts·find-my-way·mysql2·valibot이며 전이 판정이 포함된다. 감사 전체가 0이라는 뜻이 아니다. 기존 서비스 후보 이미지에서는 이 7개 패키지의 경로·모듈 해석이 모두 없었다. 새 이미지 검사는 중첩 `node_modules`까지 목록을 남겨 다시 확인한다. migration 이미지에는 CLI가 필요하므로 잔여 권고 검토와 격리된 일회성 실행 범위를 별도로 관리한다.

빌드 중 `npm ci`가 출력한 14개 항목(high 13/moderate 1)은 개발 의존성을 포함한다. 위 7개와 검사 범위가 다르므로 같은 수치로 비교하지 않는다. 잔여 권고의 조건은 [재귀 객체 병합](https://github.com/RebeccaStevens/deepmerge-ts/security/advisories/GHSA-ggr8-5vv4-36mx), [HTTP/2 요청 처리](https://github.com/delvedor/find-my-way/security/advisories/GHSA-c96f-x56v-gq3h), [MySQL 인증 처리](https://github.com/sidorares/node-mysql2/security/advisories/GHSA-3f6p-5ww8-9rcr), [검증 오류 경로 처리](https://github.com/open-circle/valibot/security/advisories/GHSA-5qjj-4xww-7phc) 등이다. 이번 CLI 사용은 저장소에서 검토한 정적 Prisma 설정·SQL과 PostgreSQL의 `migrate deploy`로 제한하며 개발/Studio 서버를 열지 않는다. 이는 실제 사용 범위에 근거한 노출 축소 판단이며 해당 라이브러리 자체의 패치를 완료했다는 뜻은 아니다.

Tiptap의 JSON `__proto__` → `mergeAttributes` → ProseMirror DOM 직렬화 재현 검사에서는 실행 속성과 상속된 공격 속성이 생성되지 않았다. 이 검사는 한 권고의 수정 동작을 확인하며, 모든 입력에 대한 보안 검사를 대체하지 않는다.

실행 중인 로컬 개발 서버의 의존성을 바꾸지 않도록 `.env`를 제외한 별도 소스 사본에 `npm ci --ignore-scripts`로 설치했다. 작업 트리의 잠금 파일과 사본의 설치 파일을 대조한다. 검증 증거는 `.media-audit/security-validation-20261010/`에 보관한다.

- 보완된 의존성으로 PostgreSQL 14.16 회귀 **265개**, Chrome 편집기 **13개**, TypeScript·변경 테스트 코드 ESLint를 통과했다.
- 첫 DB 실행은 263개 통과·마지막 2개 연결 시간 초과였다. 브라우저·타입 검사 종료 후 연결 제한을 바꾸지 않고 단독 재실행해 265개 통과를 확인했다. 첫 실패 로그도 보존한다.
- Next.js 16.3의 내부 요청 저장소 함수에 HMR 인수가 추가돼 테스트 어댑터를 맞췄다. 최초 타입 오류와 수정 후 통과 로그를 모두 보존한다.

보안 보완 후 이미지의 빌드·실행 결과는 별도로 확인해야 한다. 11.1절 이미지의 성공을 수정한 잠금 파일의 검증 결과로 대신하지 않는다.
