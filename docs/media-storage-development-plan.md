# 미디어 보관·복원·수명주기 개발 계획

작성: 2026-10-05. 상태: 조사 기록. 보관 정책의 기준이 아니다.

이후 결정과 개발 정책은 다음을 따른다.

- [코칭·코스 미디어 보관 정책](./media-library-decision.md)
- [개발 정책 1 — 보관 경로와 수명](./media-r2-folder-structure.md)
- [개발 정책 2 — 자산 데이터](./media-asset-database-design.md)

이 문서의 백업 버킷 단계와 삭제 우선순위는 그 결정에 포함되지 않는다. 아래 수치는 2026-10-05 조사 기준선으로만 참고한다.

## 1. 목표와 확인된 사실

코칭 회차와 코스 BlockNote를 유지하면서, 첨부 파일을 업로드부터 복원·삭제까지 관리 가능한 자산으로 만든다. 우선순위는 **백업·복원 검증 → 콘텐츠 참조 관리 → 미사용 검토 → 유예 삭제**다. 이후 코치 보관함과 재생 품질을 개선한다.

운영 조사 기준선(2026-10-05 10:35 KST):

- R2 전체 151개·8.19GB. 현재 저장된 DB에서 미참조 58개·4.25GB.
- 코칭 본문 미참조 22개·1.50GB, 코스 본문 28개·2.42GB. 별도 수업자료 1개·0.30MB, 커뮤니티 7개·327.67MB.
- 오디오 전체 20개 중 발행된 코칭 회차 3곳에서 각 MP3 3개, 총 9개 사용. M4A 10개와 MP3 1개는 해당 회차의 JSON·Markdown 및 다른 저장 콘텐츠에서 참조되지 않음. 합계 11개·24.76MB.
- 연결 레슨 자체가 없는 객체 9개. 커뮤니티는 DB에 참조되지만 실제 객체가 404인 파일 2개를 별도로 발견.
- 사용자 확인: 외부 백업 서비스 미사용. 서버의 확인한 cron·타이머·컨테이너·주요 파일 경로에서도 R2 백업 작업과 사본을 발견하지 못함.
- 사용자가 제공한 `Default Multipart Abort Rule`은 미완료 분할 업로드만 7일 뒤 중단. 완성된 미참조 객체는 정리하지 않음. 미완료 multipart 목록은 조회 당시 0건.
- 실제 객체 key는 `online-glia/coaching/...` 등이고 본문 URL의 논리 key는 `coaching/...` 등이다. 운영 endpoint에 버킷 경로가 포함된 현 설정의 결과이므로, 정확한 매핑을 보존해야 한다.

수량은 조사 당시의 기준선이며 향후 실행 시 고정 기대값으로 사용하지 않는다. 실행 직전 새 inventory와 DB 스냅샷을 만든다. 파일의 사용 여부는 저장된 콘텐츠 참조로 판단하고, 업로드 시각이나 동일 ETag만으로 판정하지 않는다.

## 2. 범위

### 첫 배포의 필수 범위

- DB와 R2를 함께 복원할 수 있는 백업, 실제 복원 시험, 정기 실행 및 실패 확인.
- 파일 목록과 사용처 관리, 기존 파일의 등록·대조, 기존 URL 유지.
- 코칭·코스의 업로드/저장/교체/제거와 참조의 동기화.
- 관리자의 미사용 검토, 삭제 예정, 예약 취소, 복원, 재시도 가능한 영구 삭제.
- 코칭·코스 파일 접근을 현재 사용처·콘텐츠 권한과 연결.
- 같은 버킷을 쓰는 수업자료·커뮤니티·프로필·상품 설명·강의 Q&A 등도 참조 대조에 포함. 지원하지 않는 출처는 삭제 대상에서 제외.

### 후속 범위

- 코치 미디어 보관함에서 기존 자료 검색·선택·재사용.
- 이미지 파생본, 영상·오디오 재생본, 대용량 직접/재개 업로드.
- 코스 오디오 업로드 지원은 별도 기능 결정. 현재 코스 이미지·영상, 코칭 이미지·영상·오디오 정책을 그대로 시작한다.
- 코칭권 만료 후 자료 열람 정책 변경은 별도 상품 정책 결정. 만료나 발행 상태 변경을 파일 삭제 조건으로 사용하지 않는다.

## 3. 1단계 — 백업과 복원 경로 확보

**산출물:** 백업 CLI, 검증 manifest, 복원 CLI, systemd 실행 설정, 운영 runbook.

1. 기존 R2 내 비공개 백업 버킷을 별도로 마련한다. 제안명은 `online-glia-backup`이며 아직 생성되지 않았다. 운영 앱 키는 백업 버킷에 접근하지 못하게 하고, 백업 작업은 원본 읽기/백업 쓰기 자격증명을 분리한다. R2에서 실제 지원되는 권한 범위로 검증한다.
2. `backupRunId`로 PostgreSQL 16 custom-format dump, 전체 원본 사본, 참조 목록, manifest, 앱 Git SHA·DB migration 버전, 검증 결과를 묶는다. 비밀값이 든 `.env` 자체를 평문 백업에 넣지 않는다. 필요한 설정 목록과 자격증명 복구 절차는 별도로 관리한다.
3. 첫 백업은 관련 업로드·완료 처리·본문 저장·교체·삭제를 통제하는 유지보수 절차를 갖춘다. 진행 중 쓰기를 정리하고, 동일한 DB dump에서 참조 manifest를 만든다. 사전 복사 후 유지보수 구간에서 최종 변경분을 대조해 중단 시간을 줄일 수 있다.
4. manifest에 원본 버킷/물리 key/논리 key/크기/MIME/변경 정보/백업 위치/SHA-256/검증 결과를 기록한다. R2 목록과 DB dump는 자동으로 같은 시점이 되지 않으므로 복사 전후 변경을 재확인한다. ETag를 모든 파일의 내용 해시로 가정하지 않는다.
5. VPS에서 스트리밍 CLI + systemd timer + 실행 잠금으로 시작한다. 현재 단계에서는 Redis나 별도 큐 서비스 도입을 전제하지 않는다. 객체별 checkpoint, 제한된 동시성, 실패 재시도, 마지막 검증 성공시각을 남긴다.
6. 일일 백업과 30일 복원 이력을 기본안으로 제안한다. 정기 백업도 불변 key, 기준 DB 스냅샷, 복사 중 삭제 차단, 최종 대조를 적용한다. 백업이 선점한 대상은 복사·검증이 끝날 때까지 삭제 worker가 처리하지 못하는 공통 규약을 둔다. 증분 사본은 아직 유효한 manifest가 참조하는 한 보존한다. 운영에서 지워졌다고 백업에서도 즉시 지우는 미러 방식, 증분 사본 생성일만으로 지우는 단순 lifecycle은 사용하지 않는다.
7. 삭제 예정 파일의 백업은 원본 삭제 후에도 제안 30일간 복원 가능하도록 별도 보존 기한을 둔다. 일반 백업 회전 때문에 삭제 직후 복구 사본이 사라지지 않도록 한다.

**복원 완료 기준:**

- 실행 시점 inventory의 모든 객체가 복사·검증됐고, 실패한 객체가 남은 백업을 정상 완료로 표시하지 않는다.
- 격리된 PostgreSQL 16과 테스트 버킷에 DB·원본을 실제 복원한다. 복원 앱에서 운영 DB·결제·알림·webhook 등 운영 외부 효과를 차단한다.
- 현재 사용 중인 오디오 9개, 이미지·영상 표본, 레거시 URL, Range 재생, 권한 거부를 확인한다.
- 이미 사라진 커뮤니티 파일 2개는 기존 결손으로 명시하고, 새 백업이 이를 복구한 것으로 처리하지 않는다.
- 복원 시간과 실패 대응 절차를 기록한다. 일일 백업의 제안 RPO는 24시간이며, RTO는 최초 복원 실측 후 정한다.

같은 계정의 별도 버킷은 운영 앱 실수에 대한 1차 보호다. 계정 전체 사고까지 분리하려면 별도 계정/독립 사본이 필요하며 후속 선택사항으로 둔다.

**다음 단계 운영 조건:** 복원 검증 성공 전 영구 삭제 기능은 비활성. 파일 관리 기반 개발은 병행할 수 있지만 실제 정리는 이 조건을 통과한 뒤 시작한다.

## 4. 2단계 — 파일 목록·사용처와 기존 자료 등록

**핵심 데이터 모델 제안:**

- `MediaAsset`: ID, 저장소/버킷/실제 physicalKey, 논리 key/레거시 alias, 원본명·MIME·byteSize·checksum, 업로더, 소유 범위, 업로드 완료 상태, 보관 의사, 삭제 예정일, 백업 검증 위치, 오류 이력.
- `MediaUsage`: asset과 콘텐츠의 연결 및 필드/블록 위치. 우선 `Content`와 `CoachingSession`은 실제 FK로 연결하고 정확히 한 출처를 갖도록 제약한다. 기타 출처는 출처별 참조 어댑터와 검증 규칙을 둔다. 같은 문서에서 반복 사용하면 위치 목록을 기록하고 참조 수는 정의에 맞게 계산한다.
- `MediaDeletionJob`: 대상 asset, 작업 상태, claim/lease, 시도 횟수, 재시도 시각, 오류·완료 기록. 기존 R2 삭제와 DB 변경이 한 트랜잭션이 될 수 없다는 전제로 설계한다.
- `BackupRun` 기록 또는 외부 manifest 인덱스: 전체/부분 성공, 검증 시각, 복원 시험 결과. DB가 유실되어도 R2의 manifest만으로 복원 지점을 찾을 수 있어야 한다.

`MediaAsset` 처리 상태는 `UPLOADING → READY → DELETE_PENDING → DELETING → DELETED`를 기본으로 한다. 처리 실패는 오류와 재시도 상태로 관리한다. READY의 사용 여부는 현재 참조로 계산한다. 향후 보관함에 명시적으로 보존한 자산은 참조 0이어도 자동 삭제하지 않는다.

**등록·이관 작업:**

1. 먼저 additive migration으로 테이블을 추가하고, 삭제 없이 색인만 구축한다.
2. 기존 객체를 `(provider, bucket, physicalKey)`로 멱등 등록한다. 현재 물리 key와 URL 논리 key를 별도 저장한다. 처음부터 endpoint 변경·객체 이동·본문 URL 일괄 교체를 하지 않는다.
3. 중첩 BlockNote children/미디어 props, Markdown·HTML, `Content.url`, 수업자료 objectKey, 커뮤니티·Q&A·프로필·상품 설명 등 모든 소비자를 파싱한다. 서비스의 상대/절대 프록시 URL과 확인된 레거시 R2 URL만 정규화하고, 단순 부분 문자열 검색을 삭제 판정에 사용하지 않는다.
4. JSON·Markdown 불일치, 파싱 실패, 미지원 출처, 신원 불명 객체는 삭제 보류로 표시한다. `본문 사용`, `저장된 초안 사용`, `참조 0`, `참조 불명`, `파일 누락`을 구분한다.
5. 파일별 원래 회차/레슨, 실제 사용처, 분류 이유, 백업 위치를 확인할 수 있게 한다. 현재 오디오 11개는 이관 검증 예제로 사용하되 원본 파일·회원 정보는 저장소 테스트 fixture에 넣지 않는다.

**완료 기준:** 새 inventory의 모든 객체가 등록됐거나 보류 사유를 갖는다. 현재 사용 중인 오디오 9개가 유지되고 미사용 11개는 참조 0으로 설명된다. 초기 조사 수량이 변하면 변화 이유를 확인한다. 기존 URL로 정상 재생된다.

## 5. 3단계 — 업로드·본문 저장·권한 통합

**새 업로드:** asset 예약 → 업로드 → 존재·크기·유형 검증 → READY. 업로드 후 응답을 잃거나 본문을 저장하지 않아도 파일을 식별할 수 있어야 한다. 파일 키는 충돌하지 않는 asset ID 기반 불변 키를 사용한다. 레거시 객체는 기존 key를 유지한다.

**본문 저장:**

- 서버가 PATCH의 생략 필드를 기존 값과 합쳐 최종 저장 본문에서 참조를 추출한다. 클라이언트가 주장하는 asset 목록만 신뢰하지 않는다.
- 본문과 MediaUsage를 같은 DB 트랜잭션에서 갱신한다. 코치·관리자 저장 경로 모두 적용한다.
- 초안도 사용 중으로 취급한다. 블록 제거·교체는 사용처를 제거하고 원본은 즉시 삭제하지 않는다.
- 콘텐츠·레슨·모듈 상위 삭제와 기존 `LessonMaterial` 삭제 경로도 참조 정리에 연결한다. 기존 즉시 R2 삭제 경로가 새 유예 삭제를 우회하지 않게 통합한다.
- 저장 revision으로 오래 열린 편집기의 덮어쓰기를 감지한다. 지원되지 않는 쓰기 경로가 남아 있는 동안 해당 출처의 자동 삭제는 켜지 않는다.

**접근과 URL:**

- 기존 `/api/media/r2?key=...`를 alias로 계속 해석한다. 새 자산은 asset ID 기반 안정 URL을 사용할 수 있다. 두 경로 모두 같은 권한 판단으로 연결한다.
- 회원은 현재 연결된 콘텐츠의 열람 권한으로 접근한다. 코치의 임시 업로드 미리보기·보관함 관리는 자산 소유 권한으로 별도 허용한다.
- 코스 미디어는 기존 학습 화면과 같은 수강기간 판정을 사용한다. 코칭 만료 정책은 현재 상품 정책을 유지하고 별도로 결정한다.
- 다른 회원의 개인 피드백을 URL 복사만으로 공유하지 못하게 한다. 콘텐츠 열람 권한과 다른 문서에 연결할 권한을 구분한다.
- Range의 206/416 처리와 기존 영상·오디오 재생을 유지한다. 개인 미디어 권한 응답을 공개 캐시로 바꾸지 않는다.

**완료 기준:** 업로드 취소·교체·삭제·초안·재발행·상위 삭제마다 참조가 정확히 바뀐다. DB 저장 실패는 본문과 참조를 함께 롤백한다. 파일 목록/DB 실패는 추적 가능한 상태로 남는다. 회원 간 권한 경계와 기존 링크가 유지된다.

## 6. 4단계 — 관리자 검토·유예 삭제·복원

**관리자 화면:** 사용/미사용/보류/누락/삭제 예정/삭제 실패 필터, 파일명·종류·용량, 사용처 링크, 판정 이유, 백업 상태, 삭제 예정 등록·취소·복원. 고객/코치 화면과 분리한다.

**삭제 규칙:**

1. 초기 작업은 dry-run으로만 실행한다. 전체 버킷에서 참조를 조회하지만, 자동 삭제는 참조 수집과 모든 쓰기 경로가 통합된 범위에만 허용한다. 여기서 범위는 객체 prefix뿐 아니라 그 파일을 참조할 수 있는 모든 소비자를 뜻한다. 상품·커뮤니티 등 미통합 소비자가 스캔 후 새 참조를 만들 수 있으면 해당 자산은 삭제하지 않는다. 어댑터 통합 전에는 미통합 경로에서 관리 자산을 새로 연결하지 못하게 제한하거나 계속 삭제 보류한다.
2. 관리자 검토를 마친 참조 0 자산에 `deleteScheduledAt`을 기록한다. 최초 기본안은 7일 유예다. 이는 사용 여부 판정을 미루는 시간이 아니라 복구 기회이며 업로드일이 아닌 예약일에서 계산한다.
3. 유예 중 재사용되면 예약을 취소한다. 파싱 실패·명시적 보관·미지원 출처는 계속 보류한다.
4. 실행 직전 참조 0, 해당 객체의 검증된 백업, 백업의 복원 가능 기한, 작업 지원 범위를 재확인한다. 백업 실패·불명확한 색인 상태에서는 삭제 작업을 중단한다.
5. 저장 트랜잭션과 worker가 동일한 asset 행 잠금·상태 규약을 따른다. worker가 DELETING을 선점하면 새 연결은 거부한다. 외부 R2 작업 동안 긴 DB 트랜잭션을 유지하지 않고, 선점 상태와 재시도 작업으로 관리한다.
6. R2 삭제 응답 유실·재실행·이미 없는 객체를 일관되게 처리한다. 실제 삭제 성공 후 DELETED로 확정하고, 실패는 오류와 재시도 시각을 기록한다. 제약 없이 실패 자산을 READY로 되돌리지 않는다.
7. 복원 전에 대상 삭제 예약을 취소하고 진행 중·지연된 삭제 시도가 모두 종료됐는지 확인한다. lease 만료만으로 기존 worker가 종료됐다고 가정하지 않는다. 종료를 보장할 수 없으면 같은 key 복원을 보류하거나 새 물리 generation으로 복원하고 alias를 전환하는 절차를 사용한다. 안전 조건을 통과한 뒤 검증된 사본을 원래 physicalKey로 되돌리고 상태·참조·권한을 검증한다. 객체 복원만으로 삭제된 본문을 자동 재작성하지 않는다. 콘텐츠 복원은 사용자가 검토할 별도 동작으로 구분한다.

**초기 적용:** 오디오 11개의 최신 참조를 재확인해 소수 파일로 삭제·개별 복원 시험을 수행한 후 확대한다. 나머지 미참조 후보도 같은 깊이로 검토한다. 날짜만으로 코스·코칭 prefix 전체를 만료시키는 R2 규칙은 추가하지 않는다.

**완료 기준:** 재연결/동시 저장/삭제 경쟁에서 사용 중 객체가 삭제되지 않는다. worker 재실행에 안전하고, 실패가 누락되지 않는다. 소수 파일의 삭제·복원 시험과 사후 미디어 누락 검사를 통과한다.

## 7. 5단계 — 코치 보관함과 재사용

첫 배포가 안정화된 뒤 진행한다.

- 편집기에 `새 파일 업로드 / 기존 자료 선택`을 제공한다. 검색, 종류, 미리보기, 용량, 사용처, 보관/휴지통 상태를 표시한다.
- 공통 교육 자료와 회원별 개인 자료를 구분한다. 기본 재사용은 동일 코스 또는 동일 개인 코칭 범위로 시작한다. 다른 회원 대상 사용은 명시적인 공통 자료로 등록한 자산만 허용한다.
- 보관함에 명시적으로 보존한 자산은 참조가 없다고 자동 삭제하지 않는다. 임시 업로드·미사용 자산·보관 의사를 구분한다.
- 본문 한 곳의 교체와 전체 사용처 변경을 분리한다. 파일 수정은 기존 key 덮어쓰기보다 새 버전 생성 및 명시적 연결 변경으로 처리한다.
- 크기·ETag 일치 파일을 자동 합치지 않는다. 권한·사용처를 확인하고 필요하면 내용 체크섬을 검증한 뒤 중복 관리 기능으로 제공한다.

**완료 기준:** 같은 자료를 다시 업로드하지 않고 허용된 문서에 연결할 수 있다. 개인 피드백은 다른 회원에게 노출되지 않는다. 한 사용처 제거가 다른 사용처를 깨뜨리지 않는다.

## 8. 6단계 — 전송과 재생 품질

운영 지표를 수집한 뒤 매체별로 나누어 진행한다.

- 이미지는 원본과 크기별 서비스용 파생본을 연결한다.
- 영상은 포스터·표준 재생본·적응형 재생 도입을 검토한다. 처리 비용·트래픽·운영 부담을 확인한 뒤 자체 처리와 관리형 서비스 중 선택한다.
- 오디오는 원본과 호환성 높은 재생본을 분리한다. 처리 중·완료·실패를 자산 상태와 연결한다.
- 대용량 업로드는 서명 직접 업로드·완료 검증·필요시 multipart 재개를 도입해 앱 서버의 전체 Buffer 부담을 줄인다.
- 파생본도 원본 asset에 연결해 백업·보관·삭제가 함께 처리되게 한다.

**완료 기준:** 업로드 성공률, 최초 재생 시간, 버퍼링/재생 실패율, 처리 실패율을 변경 전후 기기·네트워크 조건별로 비교한다. 현재 실측이 없으므로 임의의 성능 향상 수치를 약속하지 않는다.

## 10. 검증·배포·운영 기준

테스트 기반이 현재 package scripts에 없으므로 참조 추출 단위 테스트와 격리 PostgreSQL/R2 통합 테스트부터 마련한다. 실제 운영 원본은 테스트 fixture로 복사하지 않는다.

핵심 시나리오:

- 중첩 블록, JSON/Markdown 불일치, 인코딩된 key, 기존 절대/상대 URL, 논리/물리 prefix 매핑.
- 업로드 성공 후 응답 유실, 본문 저장 실패, 저장하지 않은 업로드, 초안, 파일 교체, 문서/레슨/모듈 삭제.
- 다중 사용처의 일부 제거, 삭제 유예 중 재연결, 저장과 DELETING 선점의 경쟁, 오래 열린 편집기 저장.
- 다른 회원 개인 자료의 열람/재사용 거부, 수강 만료, 초안 미리보기, 기존 URL로 제거된 자료 접근.
- 백업 부분 실패, 복사 중 삭제 시도, 사본 손상, 권한 오류, worker 중복·응답 유실·재시도, 동일 key 복원, 복원 중 지연된 삭제 worker의 재실행, Range 206/416.
- 미통합 소비자가 대조 이후 참조를 만드는 경우와, 모든 참조 쓰기 경로 통합 전 삭제 차단.

배포 순서는 **복원 검증 → additive migration → 삭제 없는 색인·대조 → 모든 대상 저장 경로 통합 → 권한 전환 → 관리자 검토 → 제한된 삭제 → 확대**다.

독립된 설정으로 색인, 새 저장 경로, 삭제 worker를 제어한다. 문제 발생 시 삭제 worker를 먼저 끄고 기존 URL 호환을 유지한다. 구버전 앱으로 롤백하면 참조 동기화가 빠지므로 반드시 삭제도 중단하고 재대조 전까지 재개하지 않는다. 기존 객체를 이동하지 않는 설계가 초기 롤백을 단순하게 한다.

관리 지표는 마지막 검증된 백업·복원 시험 시각, 백업 실패/미검증 수, 객체-DB 불일치, 미사용 용량, 예약/삭제 실패 수, 미디어 404·재생 실패율이다. 운영 중 삭제할 권한 없는 원본이나 출처 불명 객체를 성공 처리하지 않는다.

정책 확정과 함께 [정책 허브](/Users/gaeun/Documents/GitHub/online.glia/docs/policies.md), [코칭 정책](/Users/gaeun/Documents/GitHub/online.glia/docs/coach-coaching.md), 관련 화면 명세, [VPS 배포 문서](/Users/gaeun/Documents/GitHub/online.glia/docs/DEPLOY-VPS.md)를 갱신한다. 이 계획을 추가하는 시점에는 기존 서비스 정책을 변경하지 않는다.

## 11. 제안 일정과 결정사항

1인 개발 기준의 거친 구현 추정이며, 유지보수 일정·권한 준비·유예기간 대기는 별도다.

- 1단계 백업·복원: 3–5 개발일.
- 2단계 모델·참조 색인·이관: 3–4 개발일.
- 3단계 저장·접근 통합: 4–6 개발일.
- 4단계 관리·삭제·복원 검증: 3–5 개발일.
- 첫 배포 필수 범위 합계: 약 13–20 개발일. 5단계 보관함은 추가 3–5일, 6단계는 측정 후 별도 산정.

착수 기본안: 별도 R2 백업 버킷, 일일 백업, 30일 복원 이력, 원본 삭제 후 최소 30일 사본 보존, 삭제 예약 후 7일 유예. 기간은 구현 설정으로 분리하고 운영 적용 전에 비용·회원 자료 보관 정책과 맞춰 확정한다. 백업 보관기간은 서비스 원본 보관기간과 같은 의미가 아니다.

우선 확정할 항목은 백업 버킷/관리 접근 경로, 초기 기준 백업 유지보수 창, 허용 가능한 데이터 손실 시간, 삭제 유예/복구 보존기간이다. 코칭권 만료 후 열람기간과 공통자료의 회원 간 재사용은 후속 상품 결정이다. 이 미결사항은 읽기 전용 대조·기반 개발을 막지 않는다.
