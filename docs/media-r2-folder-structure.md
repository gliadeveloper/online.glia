## 1. 범위와 보장

코스 레슨과 코칭 콘텐츠의 이미지·영상·오디오를 보관함 자산으로 관리한다. 원본 버킷 하나를 쓰며 백업 버킷은 추가하지 않는다. 이 문서는 상품 동작과 저장소 계약, 정책 2는 이를 구현하는 데이터 계약이다. 두 문서가 충돌하면 임의로 한쪽을 우선하지 않고 함께 수정한다.

### 항상 지킬 조건

1. 사용 중인 자산과 보관 중인 자산은 용량 절감을 이유로 삭제하지 않는다.
2. 검증이 끝나고 DB에 공개 가능한 상태로 확정된 파일만 선택·재생한다.
3. 개인 보관함 접근과 콘텐츠 안에서의 재생 권한을 따로 검사한다.
4. 확정된 원본을 덮어쓰지 않는다. 같은 자산을 여러 콘텐츠에서 써도 원본을 복제하지 않는다.
5. 폐기·삭제로 확정한 작업은 늦은 저장소 응답 때문에 다시 공개하지 않는다.

### 지연 처리를 허용하는 조건

DB와 R2는 한 트랜잭션이 아니다. 중단된 업로드의 임시 파일, 최종 저장 직후 DB 커밋에 실패한 파일, 삭제 후 늦게 도착한 파일은 일시적으로 남을 수 있다. 공개 여부는 DB가 결정하고, 잔여 객체는 작업 기록과 삭제 이력을 근거로 반복 정리한다.

**DB의 작업 완료와 물리 저장량 0은 같은 의미가 아니다.** 서비스가 계속 사용 가능한 저장소에 재시도하고, 발급된 쓰기 요청이 유한하게 끝난다는 조건에서 잔여 객체를 정리한다. 저장소 장애 중 정확한 삭제 시각을 보장하지 않는다. 실패·처리 지연·잔여 용량은 운영 지표로 드러낸다.

## 2. 보관함과 콘텐츠

- 업로드 예약만으로 내 자료에 나타나지 않는다. 검증·최종 저장·DB 확정까지 끝난 자산이 내 자료에 남는다. 콘텐츠를 저장하지 않아도 다음에 다시 선택할 수 있다.
- 편집기는 공통 자료, 내 자료, 새 업로드를 제공한다. 재사용은 같은 `assetId`에 사용처를 추가하는 동작이다. 동일 파일을 새로 올린 경우의 자동 중복 제거는 이번 범위가 아니다.
- 본문에서 블록을 빼면 그 콘텐츠의 사용처만 제거한다. 보관함의 자료는 유지한다.
- 보관함에서 지우면 휴지통으로 옮기고 새 삽입을 막는다. 이미 사용하는 콘텐츠는 계속 재생한다.
- 초안도 사용처다. 미발행·수강 만료·회차 종료는 사용처 삭제 사유가 아니다.
- 개인 용량은 확정된 개인 원본의 정책상 사용량이다. 휴지통과 삭제 진행 중에는 포함하고 자산 삭제 완료 후 제외한다. 임시 객체·파생본·공통 자산은 제외한다. 실제 R2 바이트와 따로 표시한다.

팀 드라이브, 찜·폴더, 개인 자산의 공통 자산 승격, 백업·재해 복구는 이번 범위에 포함하지 않는다. `LessonMaterial`, 커뮤니티, 프로필, 상품 설명, 강의 Q&A 등 별도 출처는 이번 삭제 정책으로 정리하지 않는다.

## 3. R2 경로

R2의 폴더는 object key의 prefix다. 최종 자산은 공통/개인으로 나누고, 임시 업로드는 수명 규칙을 안전하게 적용할 수 있는 전용 prefix에 둔다.

```text
원본 R2 버킷
└── media/
    ├── shared/
    │   └── {assetId}/
    │       ├── original.mp4
    │       └── derived/
    │           ├── {thumbnailFileId}/thumbnail.webp
    │           └── {playbackFileId}/playback.mp4
    ├── personal/
    │   └── {userId}/{assetId}/
    │       ├── original.m4a
    │       └── derived/{fileId}/playback.mp3
    └── staging/
        └── {uploadId}/source.{ext}     # 공개·재생 금지, 임시 보관
```

- `{userId}`는 `User.id`, 나머지 ID도 서버가 발급한 CUID 문자열이다. 사용자 파일명은 표시용 DB 필드로만 보관한다.
- 확장자는 서버의 형식 허용표로 정하고 실제 내용을 검증한다. 원본은 자산당 하나, 파생본은 파일 ID마다 key 하나다. 썸네일과 재생본은 서로 다른 `fileId`를 갖는다.
- `staging`도 같은 버킷이다. 백업·사용자 보관함이 아니며 소유자와 scope는 DB로 구한다.
- 새 업로드의 staging은 `media/staging/`으로 통일한다. 기존 객체는 옮기지 않는다.
- 최종 `objectKey`와 그 key에 대응하는 검증된 내용은 불변이다. 실패한 업로드를 다른 내용으로 재시도하려면 새 자산 ID, 파생본 재생성은 새 파일 ID를 사용한다. ID와 key를 재사용하지 않는다.
- 코칭·코스별 prefix를 새로 만들지 않는다. 공통 원본 하나에 코스·코칭의 `MediaUsage`가 각각 연결된다.

## 4. 저장소 쓰기 계약

클라이언트와 인코딩 작업에 발급하는 업로드 권한은 해당 `stagingObjectKey`로만 제한한다. 최종 key에 대한 직접 업로드 권한은 주지 않는다. 버킷 전체 공개와 staging 공개 URL도 허용하지 않는다.

최종 저장은 서버의 준비 작업만 수행한다.

1. staging의 특정 버전을 조건부 GET으로 읽고, 제한된 작업 공간에서 내용을 검증한다. 전체 파일을 앱 메모리에 올리지 않는다.
2. 바이트 수·MIME·SHA-256과 원본 버전 식별자를 DB에 확정한다. 이 단계부터 해당 파일의 검증 결과를 변경하지 않는다.
3. 검증한 동일 바이트를 최종 key에 **조건부 생성(`If-None-Match: *`)**한다. 기존 객체를 덮어쓰는 `CopyObject`를 기본 구현으로 사용하지 않는다.
4. 이미 객체가 있거나 응답이 불확실하면, DB에 고정한 내용과 최종 객체를 대조한다. 일치하면 이어서 완료하고, 다르면 덮어쓰지 않고 격리·알림 처리한다.
5. 최종 객체 확인 뒤, 아직 유효한 작업만 DB에서 `READY`로 확정한다. 확정할 수 없는 결과는 반복 정리 대상으로 남긴다.

조건부 생성과 내용 일치 확인은 늦은 재시도가 사용 중인 파일을 변경하지 못하게 한다. DB 토큰은 작업 결과 기록을 통제할 뿐 저장소의 진행 중 요청을 취소하지 않는다. 이미 삭제된 key에 늦은 쓰기가 도착할 수 있으므로 삭제 이력을 없애지 않고 반복 정리한다.

R2의 조건부 `GetObject`·`PutObject` 지원은 [공식 호환표](https://developers.cloudflare.com/r2/api/s3/api/)를 따른다. 배포 전에 실제 사용 endpoint에서 동시 생성·조건 실패·응답 유실을 검증한다. 지원되지 않는 환경에서 무조건 PUT으로 대체하지 않는다.

## 5. 사용자 동작과 삭제

| 동작/상태 | 공개·재생 | 저장소 처리 |
|---|---|---|
| 준비 중 | 목록·삽입·재생 제외 | staging 및 비공개 최종 후보가 있을 수 있음 |
| 준비 실패·취소 | 공개하지 않음 | 폐기 기록을 남기고 잔여 객체를 정리 |
| 보관 중 | 권한에 따라 선택·재생 | 사용처가 0이어도 유지 |
| 휴지통 | 새 삽입 금지, 기존 콘텐츠 재생 유지 | key 유지, 복사하지 않음 |
| 삭제 진행 | 복원·삽입·재생 금지 | 사용처 0을 확정한 뒤 삭제 재시도 |
| 삭제 완료 | 다시 공개하지 않음 | 확인 당시 알려진 최종 객체 삭제 완료. 이력 기반 잔여 객체 점검 계속 |

휴지통 기본 유예는 30일이다. `TRASHED + READY`에서만 복원한다. 휴지통 이동 또는 마지막 사용처 제거 후 미사용·분류 완료·보류 없음이면 삭제 작업을 예약하며, 실행 예정 시각은 유예 종료보다 빠를 수 없다. 보관 중·사용 중·분류 대기·삭제 보류 자료는 예약하지 않는다. 복원과 삭제 예약 취소는 같은 트랜잭션으로 처리한다. 상태를 바꾸는 요청은 목록에서 받은 버전으로 충돌을 검사한다.

삭제 작업 선점과 복원·사용처 추가는 같은 자산 잠금으로 직렬화한다. 삭제를 선점하면 되돌리지 않는다. 일부 객체가 지워졌다는 이유로 자산을 다시 `READY`로 만들지 않는다.

## 6. 임시 파일과 잔여 객체 정리

- 정상 준비 완료와 준비 포기 모두 staging 정리를 예약한다. 최종 파일 저장 성공은 임시 파일 정리를 생략할 이유가 아니다.
- 전용 `media/staging/`에만 R2 수명 규칙을 둔다. 초기 설정은 업로드 권한 15분, 준비 작업 마감 24시간, staging 객체 만료 7일이다. 변경 시 `업로드 권한 만료 ≤ 준비 마감 < staging 만료`를 유지한다.
- staging 수명은 객체 생성 시점을 기준으로 적용되므로 늦게 도착한 객체도 대상이 된다. 만료는 즉시 삭제 보장이 아니다. [R2 수명 규칙](https://developers.cloudflare.com/r2/buckets/object-lifecycles/)의 지연을 감안해 잔여 용량을 감시한다.
- 최종 자산 prefix에는 기간 기반 삭제 규칙을 적용하지 않는다. 파일 생성일이나 사용처 0만으로 삭제하지 않는다.
- 폐기·삭제한 최종 key는 DB의 파일 기록을 기준으로 계속 점검한다. 삭제 성공 시각은 관측 기록이며 이후 검사를 막는 플래그가 아니다.
- DB에 없는 객체, 다른 기능이 참조하는 객체, 소유권·key가 불확실한 객체는 자동 삭제하지 않고 검토 목록에 둔다.
- worker 재시도와 별도로 전체 inventory 대조를 수행한다. 작업이 완료됐거나 lease가 만료됐다는 이유로 inventory에서 제외하지 않는다.

## 7. 접근 권한

- 공통 자료 등록·휴지통·복원·분류 확정: 관리자.
- 개인 업로드: 코치·관리자 본인. 코칭 대상 회원을 소유자로 넣지 않는다.
- 보관함 목록·미리보기: 본인 자료 또는 선택 자격이 있는 공통 자료. 휴지통 미리보기는 소유자/공통 관리자만, 분류 대기는 일반 보관함에서 제외한다.
- 새 삽입: 해당 콘텐츠 편집 권한과 `ACTIVE + READY` 필요. 개인 자료는 본인 소유여야 한다.
- 기존 콘텐츠 저장·재생: 현재 사용처와 해당 콘텐츠 권한으로 판정한다. 휴지통·분류 대기라도 기존 사용처는 유지할 수 있다.
- 재생은 자산과 파일이 모두 `READY`인 경우만 허용한다. 임시 key, 폐기된 파일, 삭제 중 자산을 직접 열지 않는다.

등록된 기존 URL도 DB의 자산·파일 상태와 실제 사용처를 먼저 확인한다. 삭제 이력이나 거절 결과가 있으면 예전 경로 기반 권한 검사로 우회하지 않는다. URL에 콘텐츠 문맥이 없으면 실제 사용처 중 열람 가능한 콘텐츠가 있는지 확인하거나 허용된 보관함 미리보기로만 처리한다.

짧은 재생 URL의 캐시·만료 정책도 권한 검사와 맞춘다. 이미 내려받은 바이트의 회수까지 보장하지 않으며, 신규 발급·요청 판정과 기존에 발급한 URL의 유효 기간을 구분한다. 범용 공개 R2 주소로 우회하지 않는다. 계정 비활성화는 기존 콘텐츠를 깨뜨리지 않으며, 계정 물리 삭제와 자산 소유 이전은 별도 운영 정책으로 처리한다.

현재 구현은 만료되는 GET 서명 URL 대신 안정적인 `/api/media/r2?key=...` 주소를 저장한다. 등록 자산은 매 GET·Range 요청에서 로그인 세션, ACTIVE 계정, READY 자산·파일과 미리보기/콘텐츠 열람 권한을 검사한다. 응답은 `private, no-store`와 `Vary: Cookie`를 사용한다. 업로더가 비활성화되더라도 자산을 삭제하지 않으며, 해당 업로더의 요청은 차단하고 다른 정당한 열람자의 기존 콘텐츠 접근은 유지한다.

코스 사용처는 담당 관리자·코치 또는 현재 수강 기간에 있는 ACTIVE/COMPLETED 등록자로 제한한다. 코칭은 담당 관리자·코치와 발행된 해당 회원 회차로 판정하며, 기존 상품 동작대로 코칭권 기간 만료 후에도 발행 피드백 열람을 유지한다. 요청에 `contentId` 또는 `coachingSessionId`가 있으면 그 사용처가 실제 연결되어 있어야 한다. 문맥 없는 URL은 허용된 미리보기 또는 열람 가능한 실제 사용처가 필요하다.

등록된 논리 URL뿐 아니라 현재 버킷의 물리 key로 직접 요청해도 같은 검사를 적용한다. DB에 기록된 버킷과 실행 환경 버킷이 다르면 같은 이름의 다른 객체로 대체하지 않는다. 이 프록시 정책을 보장하려면 신규 자산 버킷의 `r2.dev`·공개 도메인 등 직접 읽기 경로도 비공개여야 한다. 기존 공개 URL의 전환·캐시 정리는 배포 전에 별도로 대조하며, 프록시 URL 생성만으로 버킷의 공개 설정이 바뀌었다고 간주하지 않는다.

## 8. 기존 데이터와 배포

기존 `coaching/...`, `courses/...` 객체는 실제 key 그대로 등록한다. 본문 URL의 논리 key는 별도로 보존하며 경로를 추측해 치환하지 않는다. 소유자를 확인할 수 없으면 `UNCLASSIFIED`로 두고 기존 사용처만 유지한다.

배포 순서는 추가 스키마 → 저장 경로의 사용처 동기화 → 기존 데이터 등록·검증 → 변경분 재대조 → 보관함·새 업로드 전환 → 삭제 모의 실행 → 삭제 활성화다. 활성화 조건은 정책 2의 배포 관문을 따른다. 현재 파일을 조사 없이 옮기거나 지우지 않는다.

코스·코칭 편집기의 새 업로드는 보관함 경로를 사용한다. 기존 업로드 API와 저장된 legacy URL은 전환 호환을 위해 남긴다. 아직 자산에 등록되지 않은 기존 파일은 현재 레슨/회차 업로드 또는 이미 저장된 본문의 참조만 호환하며, 별도 감사 표시를 남겨 이후 대조한다. 보관함 간 재사용은 등록·검증한 자산으로 제공한다. 기존 미등록 경로의 다른 콘텐츠 복사를 공통 자산 선택으로 취급하지 않는다.

편집 중 다른 곳에서 본문이 바뀌면 저장을 거절하고 작성 중인 내용을 보존한다. 레슨·모듈을 삭제할 때에는 하위 콘텐츠 사용처도 함께 정리하지만, 정상 보관 중인 자산과 다른 콘텐츠에서 사용하는 자산은 보존한다. [정리 worker](./media-cleanup-runbook.md)는 기본 후보 조회이며, 명시적인 격리 실행에서만 CANONICAL 자료를 처리한다. 운영 삭제·정기 실행은 연결하지 않아 DB 삭제 예약만으로 운영 객체가 삭제되지 않는다. LEGACY·분류 대기·hold와 key 불일치는 이번 worker에서 건너뛴다.

앱과 worker의 DB 세션은 UTC로 고정한다. 과거 만료·유예·임대 시각은 DB epoch 기준으로 대조하며 자동 보정하지 않는다. 기존 데이터 점검과 운영 연결의 시간대 확인도 삭제 활성화 전 조건이다.

[읽기 전용 대조 도구](./media-audit-runbook.md)는 기존 경로와 본문·DB 자산 등록을 비교한다. 소유 미확인·주소 별칭·수업자료나 상품 등 다른 사용처를 검토할 수 있으며 파일을 등록·이동·삭제하지 않는다. 목록에 없는 파일이나 참조가 보이지 않는 파일도 관측 시각과 조사 범위를 확인한 뒤 판단한다. 현재 코치나 폴더 이름만으로 공통/개인 소유를 확정하지 않는다.

### 8.1 확인된 기존 prefix의 호환 — 2026-10-09

운영 조사에서 기존 URL의 `coaching/...`·`courses/...`와 실제 객체의 `online-glia/coaching/...`·`online-glia/courses/...`가 다른 것을 확인했다. 아바타·커뮤니티·수업자료도 같은 계약을 사용한다. 새 코드에서는 계정 호스트만 가진 `R2_ENDPOINT`와 명시적 `R2_LEGACY_KEY_PREFIX=online-glia/`를 함께 설정한다. endpoint에 버킷 경로를 붙이면 `R2_CONFIG_INVALID`로 거절한다. 새 테스트 버킷에 이 prefix를 자동 상속하지 않는다.

- 기존 `avatars/`, `community/`, `lesson-qna/`, `courses/`, `coaching/` 논리 key에만 설정한 prefix를 정확히 한 번 붙인다. 기존 업로드·서명 PUT·수업자료 읽기·기존 삭제도 동일한 위치를 사용하며 DB/본문의 논리 key는 유지한다.
- 등록 자산은 DB의 실제 `MediaFile.objectKey`를 그대로 읽는다. 새 `media/shared/`, `media/personal/`, `media/staging/`에도 legacy prefix를 붙이지 않는다. 파일 미존재 시 다른 위치를 추측해 재시도하지 않는다.
- 프록시는 원래 URL뿐 아니라 prefix를 적용한 실제 위치의 등록 여부도 확인한다. 등록된 객체를 다른 legacy 주소로 요청해도 자산 권한·상태가 우선한다. 두 자산이 동시에 후보가 되면 거절한다.
- prefix가 있는 환경에서 생성하는 새 아바타 주소는 프록시를 사용한다. 이미 저장된 공개 URL이나 버킷 공개 설정은 자동 변경하지 않는다.
- 이 설정은 모든 기존 소비자가 동일한 prefix 계약임을 대조한 버킷에만 적용한다. 혼합 경로 버킷에는 명시적 개별 매핑이 필요하며 본문·파일 위치를 추정하지 않는다.

코드와 로컬 검증은 완료했으며 운영 설정은 바꾸지 않았다. 새 앱 배포와 endpoint/prefix 설정은 같은 배포 단위로 검증한다. DB에는 항상 실제 object key를 등록하며 `urlKey`는 기존 논리 key를 보존한다. backfill·공개 접근 경로·실제 R2 업로드 검증은 별도 관문이다. [실행 기록](./production-migration-rehearsal-2026-10-09.md#7-후속-구현-r2-주소-호환)

### 8.2 기존 원본의 로컬 등록 검증 — 2026-10-10 갱신

원본 59개(약 3.84GB)를 실제 내용 검증한 뒤 별도 로컬 복제 DB에 등록했고, 콘텐츠 사용처 66개·주소/권한 3,750건·재실행 전체 재사용을 확인했다. R2 key·기존 본문 URL은 바꾸지 않았다. 소유자를 추정하지 않아 모두 LEGACY/UNCLASSIFIED와 리허설 보존 hold를 갖는다. 검증용 임시 본문은 정리했고 운영 R2 객체 쓰기·복사·삭제는 없었다.

배포 대상은 기존 서버 업데이트로 확정했다. 기존 운영 DB·R2를 유지하며 로컬 리허설 DB를 덮어쓰지 않는다. 운영용 등록·신규 업로드 공개·직접 공개 접근 점검은 별도 관문이다. [검증 결과](./production-migration-rehearsal-2026-10-09.md#9-기존-원본-검증로컬-등록-완료--2026-10-09-후속-대조-2026-10-10), [업데이트 준비](./production-existing-server-update-runbook.md).

## 9. 인수 기준

- 한 자산을 여러 레슨·회차에 넣어도 최종 원본은 하나이며, 별도 업로드 없이 다시 선택한다.
- 보관함 정리와 콘텐츠 제공이 분리되고, 사용 중인 자산은 지워지지 않는다.
- 정상·중단·재시작·늦은 응답 모두 검증되지 않은 내용이나 폐기된 자산을 공개하지 않는다.
- 임시 객체와 최종 잔여 객체가 재시도로 정리되며, 실패가 지표와 운영 검토에 나타난다.
- 정책 2의 상태 전이·장애 시나리오·SQL 검사를 통과한다. 문서 검사만으로 R2 통합 검증을 대체하지 않는다.

### 운영 공개 설정 — 2026-10-10

저장 경로는 그대로이며 새 테이블을 추가하지 않는다. 보관함 비활성 상태에서는 기존 코스·코칭 경로 업로드를 유지하고, 활성화 후 새 자산은 위 `media/shared/`·`media/personal/` 체계를 따른다. 운영 `online-glia`의 신규 자산 쓰기는 명시적으로 지정한 계정·버킷과 런타임 설정을 검증해야 허용된다. 기존 prefix는 legacy 함수에만 적용하며 새 `media/` key 앞에 붙이지 않는다. 삭제 worker는 계속 테스트 버킷에 한정한다.
