## 3. 앱 교체 전에 해결할 배포 관문

1. **공개 범위와 차단 동작:** 서버 런타임 설정과 기존 업로드 호환 경로를 구현했다(아래 3.1절). 기본값은 보관함 비활성·새 업로드 중지다. 운영 설정은 아직 변경하지 않았다. UI·직접 API 차단을 통과하더라도 운영 업로드 활성화에는 3–5번 관문이 필요하다. 삭제 worker의 운영 차단은 유지한다.
2. **운영용 등록:** 로컬에서 검증한 트랜잭션·본문 버전·원본 재확인·중복 방지·접근 검사를 운영 절차로 묶는다. 최신 DB/R2와 검증 증거를 대조하고 UNCLASSIFIED 보존 상태를 유지한다. 리허설 DB의 자산 ID나 감사 로그를 통째로 가져오지 않는다. 실제 운영 적용 명령은 아직 제공하지 않는다.
3. **R2 접근:** 직접 공개 도메인/r2.dev와 운영 origin의 CORS를 확인한다. 확인하지 않은 설정을 안전한 것으로 간주하지 않는다. 계정 endpoint와 `R2_LEGACY_KEY_PREFIX=online-glia/`는 호환 코드와 함께 반영한다. 이전 코드로 되돌릴 때에도 두 설정을 함께 복원한다.
4. **실행 이미지:** 검증한 소스의 app/migrator 이미지를 만들고 식별자를 고정한다. 현재 앱에는 검증기가 없고, 새 Dockerfile 설치 단계만으로 정상 실행이 증명되지 않는다. 실제 이미지에서 ffprobe/ffmpeg, 읽기·로그인·편집·업로드와 메모리/처리 한도를 확인한다. 서버의 앱 메모리 한도는 현재 1.5GiB다.
5. **의존성 보안 보완:** 2026-10-10 확인한 잠금 파일의 critical 1·high 13·moderate 11개 항목을 기준으로 Next.js 16.3.8, Tiptap 3.31.4, ProseMirror view 1.42.6, sharp 0.35.5와 관련 호환 패치를 반영했다. [Next.js 공식 권고](https://github.com/vercel/next.js/security/advisories/GHSA-2xp9-vwfh-vxw4), [Tiptap 공식 권고](https://github.com/ueberdosis/tiptap/security/advisories/GHSA-cp6q-959q-f8rh), [ProseMirror 공식 권고](https://github.com/ProseMirror/prosemirror-view/security/advisories/GHSA-c8x8-7fp4-3x9w). 보완 후 `npm audit --omit=dev --package-lock-only`는 **critical 0·high 6·moderate 1**이다. 남은 7개 항목은 Prisma CLI 계열의 전이 판정이며 전체 감사가 0이라는 뜻은 아니다. 서비스 이미지의 중첩 의존성 미포함과, CLI를 포함한 migration 이미지의 격리된 일회성 실행을 각각 확인한다. 새 DB·편집기 검사는 통과했으며 새 이미지 검증도 동일 잠금 파일로 완료해야 한다. Prisma 6 다운그레이드·무조건적인 `audit fix --force`·공개 포트로 Prisma 개발 도구를 실행하는 방식은 사용하지 않는다.

따라서 지금 `docker compose up -d --build`로 작업 트리를 곧바로 올리지 않는다. `npm run build`도 migration 실행을 포함하므로 빌드 검증에는 격리 환경의 `build:docker` 경로를 사용하고 운영 DB 주소를 빌드에 주지 않는다.

이미지는 운영 서버 밖에서 Linux amd64로 빌드하고 검증한 식별자로 이관한다. 4GiB Docker VM에서 Next.js 16.3.8의 Turbopack 컴파일 이후 타입 검사와 메모리가 겹쳐 커널 OOM 종료가 실제 발생했다. Dockerfile은 빌드에만 Node 힙 상한 1536MiB와 `--webpack`을 사용해 컴파일 프로세스가 끝난 뒤 메모리를 반환하도록 조정했다. 타입 검사를 끄지 않으며, 이 상한은 전체 프로세스 메모리나 앱 실행 메모리 한도를 뜻하지 않는다. 운영 앱·DB가 실행 중인 기존 서버에서 소스 빌드를 동시에 수행하지 않는다.

### 3.1 구현된 공개 설정

- `MEDIA_LIBRARY_ROLLOUT=off|admin|all`: 미설정·오타는 비활성이다. `admin`은 실제 관리자 세션의 `/api/admin` 보관함만 연다. `all`은 관리자와 코치에게 연다. 기존 콘텐츠의 재생 권한이나 사용처 동기화를 끄는 설정은 아니다.
- `MEDIA_LIBRARY_UPLOADS=enabled`: 보관함이 활성화된 역할에 한해서 예약과 완료 API를 허용한다. 기본 `disabled`에서는 보관함 조회·선택·휴지통 관리는 가능하고 새 업로드는 중지된다. 발급된 presigned PUT이나 이미 실행 중인 요청을 취소하지는 못한다. 점검 시 진행 중인 요청을 별도로 확인한다.
- `MEDIA_R2_PRODUCTION_TARGET`: 실제 계정 origin과 버킷을 합친 정확한 문자열이다. 예: `https://ACCOUNT.r2.cloudflarestorage.com/online-glia`. `online-glia` 새 업로드는 이 값 일치, `NODE_ENV=production`, `R2_LEGACY_KEY_PREFIX=online-glia/`, 비어 있는 `R2_PUBLIC_BASE_URL`을 모두 요구한다. SDK 저장소 생성과 서비스 경계에서 확인하며, 임의 저장소 객체로 운영 버킷 차단을 우회하지 않는다. 이는 배포 설정 검증이며 R2 공개 설정·IAM·CORS를 검사했다는 뜻은 아니다.

초기 배포는 `off` + `disabled` + 빈 운영 target으로 준비한다. 이 상태의 편집기는 기존 코스·레슨/코칭 회차 정보를 보내는 업로드를 사용한다. 기존 업로드 6개 API도 로그인 세션만 신뢰하도록 보완했으며 코치 레슨의 코스 ID도 검증한다. 미디어가 등록되지 않은 기존 업로드는 기존 콘텐츠 권한 확인을 계속 받는다.

브라우저는 인증된 `GET /api/{admin|coach}/media/library/capabilities`에서 필요한 불리언 값만 받는다. 응답은 `private, no-store`, `Vary: Cookie`다. 명시적으로 비활성이라는 응답을 받았을 때만 기존 경로를 쓴다. 설정 조회 실패나 새 업로드 실패를 기존 경로로 자동 재전송하지 않는다. 새 업로드 중지 상태에서 이미 사용 중인 파일을 본문에서 제거하거나 삭제하지 않는다.

검증 후 `admin` + `disabled`로 보관함을 먼저 확인한다. 운영 R2 접근·검증 자원 제한이 확인된 뒤 target을 설정하고 `enabled`로 관리자 업로드를 검증한다. 마지막에 `all`로 확대한다. 자동 삭제 worker의 `*-dev`/`*-test` 제한은 이 설정과 별개로 유지되며 운영 자산을 삭제하지 않는다. 따라서 운영 신규 업로드의 staging 정리·저장량 관찰도 활성화 전 운영 절차에 포함한다.

업로드를 급히 중지할 때는 먼저 `MEDIA_LIBRARY_UPLOADS=disabled`로 전환하고 앱에 적용한다. `off`는 기존 업로드를 다시 사용하게 하므로 전체 쓰기 중지 스위치가 아니다. Docker 환경변수는 컨테이너 생성 시 주입되므로 `.env` 파일 편집만으로 실행 중인 앱에 반영되지 않는다. 이 설정 변경에는 이미지 재빌드가 필요하지 않지만 앱 컨테이너 재생성은 필요하다.

## 4. 최종 실행 순서

1. 새 이미지·migration 해시·운영용 등록 manifest·환경설정 변경 항목·기존 이미지/Compose 복구 자료를 하나의 release 기록에 묶는다. 비밀번호·토큰의 실제 값은 기록에 포함하지 않는다. 서버의 수정된 Compose와 기존 DB 볼륨 연결을 검토한다.
2. 점검 시간을 정하고 관리자·사용자 수정, webhook, 예약 작업, 업로드 예약/완료를 포함한 쓰기를 통제한다. 진행 중인 R2 전송은 앱 중단만으로 취소됐다고 판단하지 않는다. 이번 작업에는 미참조 파일 삭제가 없다.
3. 쓰기 중단 후 기존 운영 DB의 새 전체 백업과 무결성 해시를 확보하고 복원 가능성을 확인한다. 초기 로컬 백업은 최종 시점의 데이터가 아니다. 원본 R2 목록과 바뀐 객체도 다시 대조한다.
4. 기존 운영 DB에 추가 migration을 적용한다. 기존 16개 이력과 체크섬, 신규 migration 1개의 적용을 확인한다. 기존 데이터와 새 제약·트리거를 검사한다. DB 자체를 삭제/재생성하지 않는다.
5. 최신 원본 검증과 사용처 버전에 묶인 운영용 등록을 적용한다. 누락·변경·접근 차이가 검토안과 다르면 성공 처리하지 않는다. 자동 삭제는 켜지 않는다.
6. 확인된 이미지와 endpoint/prefix 설정으로 **앱만** 교체한다. DB를 불필요하게 재생성하지 않는다. 새 앱의 실제 도메인·HTTPS·세션·코스/코칭 읽기·저장·미디어 재생과 승인된 신규 업로드 범위를 확인한다.
7. 쓰기를 재개하고 새 오류·업로드 완료·사용처 저장을 관찰한다. 최종 백업 시점, 적용 이미지, DB 변경과 재개 시각을 release 기록에 남긴다.

## 5. 실패 시 복귀

쓰기 재개 전에는 실패 지점과 DB/R2 반영 상태를 먼저 확인한다. 추가 테이블이 있다는 이유만으로 전체 DB를 옛 덤프로 덮어쓰지 않는다. 이전 앱과 새 DB의 호환이 확인된 범위에서 기존 앱 이미지·Compose·endpoint/prefix를 함께 복원한다.

새 미디어나 새 업무 데이터가 생성된 후에는 DB를 옛 백업으로 되돌리면 그 변경이 사라진다. 쓰기를 다시 통제하고 현재 DB와 새 R2 객체 목록을 보존한 뒤 수정 배포 또는 별도 역변환을 택한다. 예전 앱이 `media/` 신규 자산이나 새 권한 정책을 처리할 수 있다고 가정하지 않는다.

최종 백업, 기존 앱 이미지, 서버의 기존 Compose/환경설정은 복귀 기간 동안 보존한다. 보관 종료와 R2 물리 삭제는 이번 배포와 별도로 결정한다.
